## 三、模型怎么用（6 个工具）

- `qq_send`：发消息（text/image/at/reply_to/segments；不给目标=当前 QQ 对话，非网关会话必须显式给 group_id/user_id）
- `qq_recall`：撤回（默认最近一条）
- `qq_action`：任意 OneBot 动作（查询永远可用；写/破坏性需 `managementEnabled=true`；处理加好友/加群申请后自动清 pending）
- `qq_actions`：动作目录（按 category/keyword 过滤，含参数说明）
- `qq_events`：事件查询（kind/limit/since_seq/pending_only）
- `qq_status`：网关+账号状态（连接、心跳、生命周期、事件计数、最近发送记录）

事件通知回合有一条硬规则：**助手直接输出的文字不会回传 QQ**（模型要发消息必须显式调工具），避免模型看到「某人被设为管理员」就往群里发一句话。

## 九、M6.4 修复（2026-10-17 19:01）：同一条 QQ 消息回两遍

用户截图指出：群里一次提问，机器人连发两条。根因在真机日志里一眼可见（`m4-gateway.log` turn 75–82）：每个回合都是 `tool qq_send -> group ... message_id=xxx` 紧接 `relayed turn 75 (23 chars, text) to group ...` —— 出站有两条通道（工具显式发 + 回合结束自动回传助手文字），模型两条都用了就双发。

**修法**（`lib/gateway/gateway.js`）：

1. `sendMessage` 记账「工具往哪个对话发过带文字的消息」（目标 + rid）；纯图片/文件不记，避免发图后的解释文字也被吞。
2. 回合收尾 `relayAssistantText` 先查本回合有没有工具发送；有 → 跳过自动回传，`duplicateRepliesSuppressed` +1，日志 `assistant text NOT relayed ... avoid double send`。
3. 新配置 `relayDedupeMode`：`turn`（默认，去重）/ `off`（旧行为，可复现双发）。
4. 投给模型的来源说明改口径：纯文字直接输出即可回传；已用 `qq_send` 发过文字时最终文字不再自动回传。

**核验**：

- 离线 `test/m6-4-dedupe.mjs` **7/7**：工具文字→压掉回传；无工具→照常回传；纯图片→解释仍回传；空闲工具发送不误伤；群聊 number/string 群号能对上；`off` 对照组能复现双发。
- 真机 `test/m6-4-live-dedupe.mjs` **4/4**：在运行中的网关上临时以假 NapCat 端注入一条主号私聊（真 QQ 端零消息），QQ 网关会话真跑了一回合；日志 turn 83 先 `tool qq_send -> private 10001`，紧跟 `assistant text NOT relayed ... (11 chars)`，只抓到 1 条 `send_private_msg`，`duplicateRepliesSuppressed` 0→1、`relayed` 不变。
- 热重载：patch 加 `relayDedupeMode: turn` 后网关自动重启一次（EADDRINUSE 重试后接上），NapCat 自动重连，不用扫码。
- 离线全量回归：m1 22/22、m2 27/27、m3 14/14（字段数 37→38 同步）、m4 9/9、m5 17/17、m6 32/32、actions 36/36、events 24/24、container-proxy 5/5、markdown-image 12/12，两个变异测试照旧被抓到。

**回滚**：patch 里把 `relayDedupeMode` 改成 `off` 即回旧行为（代码保留）；本次修复前快照 `m6-4-snapshot-20261017.tar.gz`。

## 十一、M6.6 功能（2026-10-18 13:00）：合并转发（QQ 聊天记录）能读出来了

**问题**：群里/私聊发来一条「合并转发（聊天记录）」，网关不投给模型，只回一句「目前仅支持文本消息」。不是安全顾虑，是没接：NapCat 不会把转发内容塞进消息事件（`parseMultMsg: false`，只给一个转发 id），而网关只认文字/图片段，`forward` 段被当成不支持的媒体。

**做法**（`lib/gateway/protocol.js` + `lib/gateway/gateway.js`）：

1. `forward`/`node` 段不再算「不支持的媒体」：纯转发消息能进门（以前会被当空消息丢弃），也不再回「目前仅支持文本消息」。
2. 收消息时按 `segment.data.id` 调 `get_forward_msg`，把返回的节点压成文字：`1. 小明：第一条`（图片 `[图片]`、语音 `[语音]`、@ 带号码、嵌套转发标 `[合并转发]`）。
3. 有界：一条消息最多 3 段转发、每段最多 50 条节点 / 4000 字，超出写明「共 N 条，只展示前 M 条」。
4. 读取失败不静默：prompt 里写「[合并转发消息，内容读取失败：原因]」，回合照常可回传，不卡单飞闸门。
5. 协议端若已 inline 展开内容（`data.content`），直接用、不再多发动作。
6. 真机实测的坑：`get_forward_msg` 只认转发 id（`res_id`/`forward_id`）；传普通 `message_id` 会报「消息已过期或者为内层消息」。解析 id 的顺序已按 `id > res_id > forward_id > message_id` 固定。

## 十二、M6.7 功能（2026-10-18 13:07）：合并转发里的图片也能看了

**问题**：M6.6 只把转发节点压成文字，图片只剩 `[图片]` 两个字的标签——模型知道「有张图」，但看不到图。用户实拍的例子：小志转发的购物截图（始祖鸟冲锋衣），模型只能回「没看，只拿到 id 和占位」。

**做法**（`lib/gateway/protocol.js` + `lib/gateway/gateway.js`）：

1. `formatForwardNodes` 新增 `maxImages`：节点里的图片按出现顺序编号成 `[图片1]`、`[图片2]`…，同时收集 `{label, nodeIndex, who, file, url, summary}`。`maxImages=0` 时保持旧的 `[图片]` 标签（旧调用点不变）。
2. 网关按编号真下载（复用 M4.1 的 `resolveImage`：url → base64://file → http file → `get_image` 动作），作为独立 image 内容块投给模型。
3. 正文块后面加一行映射 `[合并转发里的图片] 图片1=第2条（小明）；图片2=…`，模型能把图和「第几条、谁发的」对上。
4. 单段转发最多挑 9 张（`MAX_FORWARD_IMAGES`），且不超过本回合剩余图片额度（宿主单条消息 20 张）；超出的图保留 `[图片]` 标签，不下载。
5. 某张下载失败写 `[图片N 下载失败：原因]` 占位，其余照投、整条消息不算失败。
6. 只收集真正展示出来的节点的图（被 `maxNodes`/`maxChars` 截断的节点不下载）。

**核验**：

- 离线 `test/m6-7-forward-images.mjs` **8/8**：编号收集、maxImages=0 兼容、截断与上限、真下载 4 张图进 prompt、下载失败占位、12 张只下 9 张、文字+直发图+转发图混合、inline 不重复请求、计数自洽。
