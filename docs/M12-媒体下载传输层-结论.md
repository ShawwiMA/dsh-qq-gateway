# M12 媒体下载传输层校验结论（2026-10-27，评审第三轮）

背景：评审 #99 第三轮指出三点——**媒体地址校验还需覆盖 IPv4 映射 IPv6；校验实际连接地址与重定向；下载需要在读取过程中执行大小上限**。本里程碑修这三项，目标 1.0.6。

## 一、问题

1. IPv4 映射 IPv6 只认了 `::ffff:1.2.3.4` 这种带点分写法的形态；`::ffff:7f00:1`（十六进制压缩）会被当成普通公网 IPv6 放行，绕过整个私网判定。
2. DNS 重绑定窗口：校验时解析一次、下载时再解析一次，两次结果可以不一样；实际连到的地址没有核对。
3. 大小上限在「读完整包之后」才检查，慢速大文件能先把内存撑爆。

## 二、修复（1.0.6）

1. `url-guard.isPrivateIp()` 重写 IPv6 判定：完整解析（`::` 压缩、内嵌 IPv4），覆盖
   - IPv4-mapped（`::ffff:a.b.c.d` 与 `::ffff:xxxx:xxxx` 两种写法）
   - IPv4-compatible（`::a.b.c.d`）
   - NAT64（`64:ff9b::/96`）、6to4（`2002::/16`）：拆出内嵌 IPv4 再判
   - Teredo（`2001::/32`）、ULA（`fc00::/7`）、链路本地（`fe80::/10`）、组播、文档段（`2001:db8::/32`）、`::`、`::1`
2. `safeFetchMedia()` 生产路径改为 node:http/https 自连（`downloadHttp`）：
   - 自定义 `lookup` 把「解析并校验过的 IP」**钉死**为实际连接地址（单次解析，没有重绑定窗口）；Host 头 / SNI 仍用域名；
   - 连上后核对 `socket.remoteAddress`，非白名单地址直接断开；
   - 重定向逐跳、每跳重新解析校验，最多 3 跳；
   - **边读边计数**，超过 `maxBytes` 立即销毁请求（Content-Length 声明超限直接拒）。
3. 离线测试路径（注入 `fetchImpl`）保持不变，方便回归；生产不注入时一律走自连路径。
4. 新增 `test/m12-media-transport.mjs`（8 条断言）：IPv6 全形态、IPv6 URL、前置拒绝、解析层拒绝、钉 IP 连接、302 跟随、流式限长（服务端观测到客户端中断）、小上限中断。

## 三、验证

- `node test/m12-media-transport.mjs`：8/8 通过；
- `npm test`：23 套离线套件全绿。

## 四、残余风险

- 主号回合的 URL 直传仍由 NapCat 下载（主号是所有者，可控范围）；其重定向不受网关校验。
- HTTPS 证书校验依赖系统 CA；内网自签名服务在 allowPrivate 放开时仍会因证书失败，属预期。
- 若需要「连接前先探测」更复杂的网络策略（如 egress 白名单），建议在 NapCat 容器层加网络隔离，网关层只能做到本层校验。
