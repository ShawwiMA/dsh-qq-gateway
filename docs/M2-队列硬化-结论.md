## 本轮抓到 2 个真 bug（都在 `ws.js`，不是测试问题）

1. **主动 `close()` 之后 `'close'` 事件不再触发**：`WsPeer.close()` 先把 `closed` 置 true，socket 真正关闭时处理器看到 `closed` 就 return，于是网关的 `peers` 集合永远留着这条死连接 —— 后面的回传会写进空气而不是进补发缓冲。"断线补发"用例第一次跑就是这个表现（`peers` 一直不归零）。修法：另加 `notified` 标志，socket 真关时保证发一次 `'close'`。
2. **`connectWs` 客户端把"和 101 响应挤在同一 TCP 段的帧"直接丢掉**：`WsPeer.emit` 对没人监听的事件是丢弃的，而原先 `peer.feed(restBytes)` 在 `resolve()` 之后同步执行，调用方还没来得及挂监听器。补发的回传正好和握手响应挤在一起，于是"发了但收不到"。修法：`resolve` 之后用 `queueMicrotask` 再喂。

## 断言覆盖（对着这轮的三条要求）

- **超时**（5 条）：超时计时≈800ms、不推 QQ、`timedOutRids` 记账、排队的那条被自动放出来（闸门确实放了）、迟到 `turn/end` 归到 `skippedTimeoutLate` 且零回传、超时回合不影响后续回合回传、真机形态（`user/message` 早到 + `turn/end` 迟到）同样只记 timeout。
- **断线重连**（4 条）：断线期间的回传进缓冲不丢、断线期间外来回合零补发、重连自动补齐且只补一次、重连后新消息照常往返。
- **溢出丢最旧**（2 条）：`maxQueue=2` 时压到上限且 `overflowDropped=2`、实际投递顺序 = 第 1、4、5 条（2、3 条被丢）。
- **token 轮换**（3 条）：旧 token 立刻 401、新 token 立刻可用、已建连接不被踢（有意为之）；空 token 有启动警告、`setToken` 后立刻要 token。
- **媒体回执**（7 条 + 单元 3 条）：纯图片回 `目前仅支持文本消息` 且不投宿主不占回合、语音回执、节流窗口内不重复回、窗口过后可再回、同 `message_id` 不重复回、空白文本不回执、图文混合照常投递且不触发回执。
- 另有状态字段齐全性 1 条、红线回归 1 条（GUI 回合在媒体回执存在时仍零回传）。

## 测试自身的坑（如实记录）

M1 的"去重"用例等的是 `replies().length >= 2`。M2 加了媒体回执后，这个条件被**别的**回执提前满足了，用例提前返回，导致后面两个用例的计数基线被带偏（首轮 19/24 里的 2 条就是这么来的）。已改成等"本回合自己的那条回传"（`=== repliesBefore + 1`）。

## 留到 M3 / M4

- 超时后**不主动 abort** 已投递的 prompt：abort 语义没在真机验证过，宁可只放本地闸门（已写进文档）。
- token 轮换只影响新握手，不踢已建连接（有意为之）。
- 无 peer 在线时，一次发送会同时计 `sendFailures` 和 `offlineBuffered`（语义已固化，M3 状态页按此展示）。
- M3：Config Schema + `GET /dsh-qq-gateway/status`（`status()` 字段已齐，含 `offlineBufferDepth` / `timedOutRids`）。
- M4：Docker NapCat + 小号一次性真机验收。
