# M14 生产调用链校验结论（2026-10-27，评审第四轮）

背景：评审 #99 第四轮指出——**实际媒体调用仍把默认 fetch 传入，走到了测试下载分支，因此连接地址绑定和逐跳大小限制没有生效；再检查 6to4 地址中的 IPv4 提取；补充覆盖生产调用链的测试**。本里程碑修这三项，目标 1.0.7。

## 一、问题（都是真问题）

1. **生产实际没走加固后的下载路径。** `gateway.js`、`media.js` 写的是 `deps.fetchImpl ?? globalThis.fetch`，然后原样传给 `safeFetchMedia`。只要传进去的是函数，`safeFetchMedia` 就判定「测试注入了假 fetch」，走 `fetchBased`（用 undici 的全局 fetch 下载）。结果：M12 做的钉 IP、`socket.remoteAddress` 核对、边读边限长**全部没有生效**，只有关掉 DNS 双解析之外的旧式校验在跑。M12 的测试直接调 `safeFetchMedia`（不注入 fetch），所以测的是正确分支，测试全绿但生产没用上——测试覆盖不到「调用方怎么传参」。
2. **6to4 内嵌 IPv4 取错位置。** 6to4（`2002::/16`）的内嵌 IPv4 在**第 3–6 字节**（bits 16–47），原代码和其它过渡形态一起从**尾部**（第 13–16 字节）取。于是 `2002:c0a8:101:808:808:808:808:808`（内嵌 192.168.1.1，尾部字节恰好是 8.8.8.8）被判成公网放行。

## 二、修复（1.0.7）

1. `gateway.js` / `media.js`：不再默认全局 fetch，只认「显式注入的函数」；`safeFetchMedia` 再做一层防御——传进来的若是 `globalThis.fetch` 本身，按「没注入」处理，仍走 node:http 自连。这样以后即使有人把默认值写回去，也不会静默退化。
2. `isPrivateIp()` 的过渡机制按各自真实位置取内嵌 IPv4：
   - 6to4 `2002::/16` → 字节 2–5；
   - IPv4-mapped `::ffff:0:0/96`、IPv4-compatible `::a.b.c.d`、NAT64 `64:ff9b::/96` → 尾部字节 12–15；
   - 新增 IPv4-translated `::ffff:0:0:0/96`（尾部）、NAT64 本地用途 `64:ff9b:1::/48`（整段拒）、ISATAP（接口标识 `0000:5efe:<IPv4>`）。
3. 下载结果加 `transport` 字段（`node-http` / `fetch`），谁走了哪条通道一目了然，测试直接断言。
4. 新增 `test/m14-production-chain.mjs`（11 条）：6to4 回归、其它过渡形态、三档通道选择，然后用**真网关 + 真本地 HTTP 服务器**跑生产调用链——全局 fetch 换成会抛错的桩，验证入站图片下载、出站非主号 URL 代下载、流式限长中途掐断、重定向逐跳重新校验（第 2 跳 `file://` 被拒）、死循环按跳数拒绝，最后断言全局 fetch 调用次数为 0。

## 三、验证

- 旧代码跑 m14：**0/11**，全局 fetch 被调用 5 次（复现评审指出的问题）。
- 新代码跑 m14：**11/11**。
- `npm test`：25 套离线套件全绿（含 m1–m13 回归）。

## 四、残余风险

- 主号回合的 URL 直传仍由 NapCat 容器下载，重定向不受网关校验（主号是所有者，属于既定信任边界）。
- 全局 fetch 的其它用途（与本模块无关）未受影响；本次只把「媒体下载」这条路的注入语义收紧。
- 6to4 若内嵌公网 IPv4，仍会放行并按 IPv6 连接——这符合 6to4 的语义（实际对端就是那个公网地址），只是部分老旧网络会经中继，是否额外加「禁 6to4」开关可按部署环境决定，默认不加。
